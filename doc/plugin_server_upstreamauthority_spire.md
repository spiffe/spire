# Server plugin: UpstreamAuthority "spire"

The `spire` plugin uses credentials fetched from the Workload API to call an upstream SPIRE server in the same trust domain, requesting an intermediate signing certificate to use as the server's X.509 signing authority.

The SVIDs minted in a nested configuration are valid in the entire trust domain, not only in the scope of the server that originated the SVID.

In the case of X509-SVID, this is easily achieved because of the chaining semantics that X.509 has. On the other hand, for JWT-SVID and WIT-SVID, this capability is accomplished by propagating every JWT-SVID and WIT-SVID public signing key to the whole topology.

## CA lifetimes

The downstream server requests an X.509 CA with its configured `ca_ttl`. The upstream server caps the issued CA's expiration at the effective expiration of its own signing CA chain. Consequently, a downstream CA can have a shorter lifetime than the downstream server requested.

To consistently obtain the full requested downstream CA lifetime during normal scheduled rotation, plan for:

```text
downstream ca_ttl <= min(upstream CA lifetime / 6, 7 days)
```

When the upstream CA receives its full configured lifetime, this means setting the upstream `ca_ttl` to at least six times the downstream `ca_ttl`, and keeping the downstream `ca_ttl` at or below seven days. Allow additional margin for clock skew and rotation scheduling delays. If the upstream server also uses an upstream authority, account for its actual usable CA lifetime, which may be shorter than its configured `ca_ttl`.

Apply this relationship independently at every nesting level, and apply the [CA and SVID lifetime relationship](/doc/spire_server.md#ca-and-svid-lifetimes) to each server's SVID TTLs. For example, downstream SVID TTLs of at most one hour, a downstream `ca_ttl` of eight hours, and an upstream `ca_ttl` of 64 hours provide margin above both six-times relationships, assuming the upstream CA receives its full requested lifetime.

The seven-day cap applies at each hop: increasing the upstream `ca_ttl` alone cannot ensure that a downstream CA requested for more than seven days always receives its full lifetime. These relationships concern obtaining the requested lifetime; a shorter-lived CA or SVID can still be usable.

JWT-SVID and WIT-SVID signing keys are generated by each server with its own `ca_ttl`; their lifetimes are not capped by the upstream X.509 CA chain.

## Configuration

The plugin accepts the following configuration options:

| Configuration       | Description                                                                  |
|---------------------|------------------------------------------------------------------------------|
| server_address      | IP address or DNS name of the upstream SPIRE server in the same trust domain |
| server_port         | Port number of the upstream SPIRE server in the same trust domain            |
| workload_api_socket | Path to the Workload API socket (Unix only; e.g. the SPIRE Agent API socket) |
| experimental        | The experimental options that are subject to change or removal               |

These are the current experimental configurations:

| experimental                 | Description                                                                                               | Default |
|------------------------------|-----------------------------------------------------------------------------------------------------------|---------|
| workload_api_named_pipe_name | Pipe name of the Workload API named pipe (Windows only; e.g. pipe name of the SPIRE Agent API named pipe) |         |
| require_pq_kem               | Require use of a post-quantum-safe key exchange method for TLS handshakes                                 | false   |

Sample configuration (Unix):

```hcl
    UpstreamAuthority "spire" {
        plugin_data {
            server_address = "upstream-spire-server",
            server_port = "8081",
            workload_api_socket = "/tmp/spire-agent/public/api.sock"
        }
    }
```

Sample configuration (Windows):

```hcl
    UpstreamAuthority "spire" {
        plugin_data {
            server_address = "upstream-spire-server",
            server_port = "8081",
            experimental {
                workload_api_named_pipe_name = "\\spire-agent\\public\\api"
            }
        }
    }
```
